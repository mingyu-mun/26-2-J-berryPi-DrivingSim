# 06. 실측 모드 (DEMO) — 라즈베리파이 → 시뮬레이터

> 상태: **틀만 구현된 데모**입니다. 전송 방식이 아직 정해지지 않았으므로 메뉴에서 고를 수 있게 해 두었습니다. 지금 실제로 동작하는 것은 **UDP** 하나입니다. Serial, MQTT, WebSocket은 설정 화면과 클래스 자리만 있습니다.

```
 센서(ECG·PPG) ─▶ 라즈베리파이 (센서 허브) ──[전송 방식?]──▶ PC: Unity LiveBioSource ─▶ AiLink ─▶ 추론 서버 (S1-EP + 상태 머신 v2)
                                                              (UDP 5010)                    (UDP 5005/5006, 03_규약 3절)
```

## 1. 패킷 형식 (모든 전송 방식 공통)

JSON 한 개가 묶음 하나입니다. 기본 10 Hz로 보냅니다(100 ms마다).

```json
{"type": "bio", "device": "rpi-01", "seq": 123, "t_dev": 12.30,
 "fs_ecg": 435.33, "fs_ppg": 100.66,
 "ecg": [336.0, 349.0, ...], "ppg": [156115.0, 155933.0, ...]}
```

| 필드 | 의미 |
|---|---|
| `seq` | 1씩 늘어나는 번호입니다. 수신 측은 건너뛴 번호를 **손실**로 셉니다. |
| `t_dev` | 장치 시계 기준으로 이 묶음의 첫 표본 시각[s]입니다. 시간축은 도착 시각이 아니라 이 측정 시각으로 맞춥니다 (웹보드 규약 3장). |
| `fs_ecg`, `fs_ppg` | 각 채널의 샘플링 주파수입니다. 첫 패킷에서 정해지고, 추론 서버 hello에 그대로 쓰입니다. |
| `ecg`, `ppg` | **원신호** (필터·전처리 없음). 전처리는 PC의 추론 서버가 저장소 코드로 합니다. |

크기는 ECG 500 Hz + PPG 100 Hz 기준 묶음당 약 60개 값, 0.5~1 KB입니다. UDP 한 데이터그램에 충분히 들어갑니다.

## 2. 전송 방식 비교 (지연 질문에 대한 답)

**결론: MQTT를 써도 지연 때문에 판정이 힘들어지지는 않습니다.**
- 판정 단위가 **30초 창, 10초 간격**입니다. 출력도 창 끝 + 5초 뒤에 나옵니다.
- 같은 LAN 안에서는 어떤 방식이든 지연이 수 ms~수십 ms 수준이라 판정 결과에는 영향이 거의 없습니다.
- 지연보다 중요한 것은 세 가지입니다.
  1. 손실과 순서 뒤바뀜이 생겼을 때 알아챌 수 있는가 (`seq`)
  2. 시간축을 측정 시각으로 맞추는가 (`t_dev`)
  3. Wi-Fi가 잠깐 끊겼을 때 버퍼링하는가

| 방식 | 지연 (같은 LAN, 일반적) | 장점 | 주의 | 상태 |
|---|---|---|---|---|
| **UDP** (Wi-Fi/이더넷) | 수 ms | 가장 단순합니다. 브로커가 없고, 이 시뮬레이터와 같은 방식입니다. | 손실과 순서 뒤바뀜이 생길 수 있어 `seq`로 확인합니다. Wi-Fi 절전 때문에 흔들림이 커질 수 있습니다. | **구현** |
| Serial (USB-UART / USB 가젯) | 1 ms 안팎, 흔들림 최소 | 네트워크 설정이 필요 없고 가장 안정적입니다. | 케이블이 필요합니다. 921600 bps면 ECG 500 Hz + PPG 100 Hz(JSON 기준)를 보낼 수 있고, 이진 포맷이면 여유가 큽니다. | 틀 |
| MQTT (mosquitto) | 수~수십 ms (QoS 0) | 웹보드, 시뮬레이터, 기록기가 **같은 데이터를 함께 구독**할 수 있습니다. 재연결이 쉽습니다. | 브로커가 필요합니다(라즈베리파이에 mosquitto). QoS 1·2는 재전송 때문에 지연이 튈 수 있습니다. | 틀 |
| WebSocket | 수~수십 ms | 웹보드 규약이 제안하는 단일 채널입니다. 브라우저 대시보드와 같은 서버를 공유할 수 있습니다. | TCP라 손실은 없지만 재전송 때 지연이 튈 수 있습니다(head-of-line). | 틀 |

**제안**
- 시연 PC와 라즈베리파이가 같은 공유기에 있다면 **UDP로 시작**합니다.
- 웹보드도 같은 생체 데이터를 실시간으로 받아야 한다면, 라즈베리파이에 **MQTT 브로커**를 두는 구성을 검토합니다. 토픽은 `jberry/bio`로 하고, 시뮬레이터·웹보드·기록기가 각각 구독합니다.
- 메뉴의 **수신 시험** 화면에서 패킷/초, 손실, 도착 흔들림(ms), 마지막 수신 경과를 바로 볼 수 있습니다. 실제 망에서 이 숫자를 재 보고 결정하면 됩니다.

## 3. PC 한 대로 시험하기 (라즈베리파이 없이)

```bash
# 1) Unity Play → 메인 메뉴 > 실측 모드 > UDP · 포트 5010 > [수신 시험 시작]
# 2) 다른 터미널에서 기록을 실시간 속도로 보냄 (실측 기록 또는 합성 파형)
python Tools/rpi_bridge/rpi_sender.py --session Assets/StreamingAssets/Replays/rec_20261118 --start 900
python Tools/rpi_bridge/rpi_sender.py --synthetic
# Wi-Fi 상황 흉내: 패킷 2% 손실 + 송신 흔들림 15 ms
python Tools/rpi_bridge/rpi_sender.py --session <폴더> --loss 0.02 --jitter 15
# 3) 수신 상태가 '수신 중'이 되면 개인 기준을 고르고 [실측 주행 시작]
```

- 라즈베리파이에서 보낼 때는 `--host <PC IP>`를 씁니다. Windows 방화벽에서 UDP 5010 인바운드를 허용해야 합니다.
- `rpi_sender.py`는 표준 라이브러리만 씁니다. 송신 루프에서 기록을 자르는 부분(`ecg[ie0:ie1]`)을 실제 센서 버퍼 읽기로 바꾸면 라즈베리파이 송신 코드의 출발점이 됩니다.

## 4. 개인 기준 (baseline)

- **자동 수집**: 실측을 시작한 뒤 60초 착석 대기를 거치고, 깨끗한 30초 창 20개를 모읍니다(보통 7~8분, 최대 10분). 상태 머신 v2의 2장과 같습니다.
- **기준 측정 파일**: 미리 측정한 안정 상태 기록(`role: baseline`)으로 기준을 정하고 바로 판정을 시작합니다.
  - 다만 5분 스케일 RR 특징은 실측이 시작된 뒤 300초가 지나야 채워집니다. 그동안 화면에 "장기(5분) 특징 창 채우는 중 n%"를 표시하고, 판정은 보수적으로 나옵니다.

## 5. 남은 구현 (실측 모드를 실제로 쓰려면)

1. 전송 방식을 확정하고, `LiveBioSource`의 해당 Transport 수신부를 구현합니다. 현재 `StartListening`에서 "아직 구현 전"을 표시하는 자리입니다.
   - Serial: `System.IO.Ports`(API 호환성 수준 .NET Framework 필요) 또는 별도 Python 중계기를 씁니다.
   - MQTT: MQTTnet 패키지를 쓰거나, 추론 서버(Python, paho-mqtt)가 직접 구독하는 구조를 검토합니다.
2. 장치 시계(`t_dev`)와 PC 시계를 맞춥니다. NTP를 쓰거나, 첫 패킷 기준으로 오프셋을 계산합니다. 현재는 받은 표본 수로 세션 시각을 계산합니다.
3. 센서별 실제 샘플링 주파수와 결측 처리를 확인합니다 (전극 분리 신호를 `null`/NaN으로 보낼지).
4. 웹보드로 보내는 이벤트의 `origin=live`는 이미 처리되어 있습니다 (03_규약 4절).
